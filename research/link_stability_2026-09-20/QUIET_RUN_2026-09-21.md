## ⚠ Two things happened mid-run — read before analysing (added 2026-09-21T12:20Z)

### 1. `iw2ohx-monitor` was NOT quiet. It resumed 15 minutes into the run.

The table below says the macmini LaunchAgent was "unloaded". It was — and then
**`net.iw2ohx.quiet-run-restore` fired 22 hours early and put it back.** Its
`StartCalendarInterval` carries only `Hour`/`Minute`, no `Day`/`Month`, so it is
not one-shot: it fires at 12:30 **every day**, and the first one it hit was
**2026-09-21**, not the 22nd.

Evidence — `~/.config/quiet-run/restore.stdout.log`:

```text
2026-09-21T10:30:03Z  monitor reload FAILED
```

and `~/iw2ohx-monitor/logs/launchd.stdout.log`, one `[done]` line every ~30 min
from `12:30:35 CEST` (= 10:30Z) onward, with a single 45-min gap 11:45 → 12:30
(the 15 minutes it was actually unloaded, plus the missed cycle).

So **the run was genuinely quiet from 10:15Z to 10:30Z and no longer.** From
10:30Z a 30-minute SSH probe of every host has been inside every measurement
window again. Two mitigations on the facts:

- The **big** poller is still off: `station-dashboard`'s 15-min telnet of all
  five nodes, including the chained hop to `-12`, is a **gw crontab** entry and
  `crontab -l` on gw still shows only `ping-iw2ohx2.sh`. The finding this run was
  built around is still controlled for.
- The monitor's `xnet-tnc4e` probe reads the node's **HTTP CGI**, not telnet, so
  it does not trip the [`TELNET_SLEEP_FREEZE`](TELNET_SLEEP_FREEZE.md) path. Its
  telnet exposure is the **recovery** action, which only fires on the `reverted`
  metric — and it did fire, see below.

The restore script's own success check reported `FAILED`, so the `&&` self-unload
never ran and the agent is **still loaded**. Its next fire (tomorrow 12:30 CEST)
is the originally intended one, so the intended restore still happens; it will
then keep firing daily until unloaded. **Fix the plist (add `Day`/`Month`, or
unload it) before relying on this pattern again** — a one-shot LaunchAgent needs
a dated `StartCalendarInterval`.

### 2. The topology changed at ~12:00Z: `IW2OHX-4` is out of the picture

On Marco's decision, `IW2OHX-4` was cut back to a **single** FlexNet link (to
`IW2OHX-12`). Both LinBPQ instances had their `MAP IW2OHX-4 …` line and locked
`IW2OHX-4` route commented out and **were restarted**, and the corresponding
ports were detached on the node. Consequences for this run:

| Capture | Effect |
|---|---|
| `/tmp/rtr-mon-4` | **flatlines from ~12:00Z** — there is no `-4` link left to capture |
| `/tmp/rtr-mon-12` | **the question, still valid and still recording**, but with a session discontinuity at the IR2UFV restart |
| `/tmp/rtr-mon-14` | same discontinuity |
| `/tmp/prod-router-watch` | same discontinuity; prod's only FlexNet peer is now `-14` |

`IR2UFV` now has **two** peers (`-14`, `-12`) instead of three, so
advertisement volume, `learned[]` size and the cost landscape all moved again —
the same class of break that already made the `tfix-mon-*` captures
incomparable. **Treat 10:15Z→12:00Z and 12:00Z→10:15Z(+1) as two separate
populations.** The upside: with `-4` gone, `-12`'s remaining peers are only
`-14` and `IR2UFV`, so the `IR2UFV ↔ -12` teardown question is now being asked
on a strictly simpler graph, and the `-14 → -13 → -4 → -12 → -14` cycle no
longer exists.

Also worth knowing when reading the `-4` pcap: at **12:02Z the monitor's
auto-recovery fired against `-4` and rebuilt both retired ports** (it still had
the pre-change probe logic, for which "port 4 missing" *was* the reboot
signature). They were torn down again at ~12:10Z once the probe and the recovery
script were inverted. Anything on `-4` between 12:02Z and 12:10Z is that, not the
protocol.

## What makes this run different: nothing is polling the nodes

This is the point of the run. From this project's own history — *"the
monitoring caused most of what it measured"* — and it was worse than that
note implies:

| Poller | Was doing | Now |
|---|---|---|
| `station-dashboard` cron, gw | telnet **all five** nodes every **15 min**, including a chained hop to `-12` **across the live mesh** | **disabled** |
| `xnet-web-status` cron, gw | telnet `IW2OHX-14` every **10 min** | **disabled** |
| `iw2ohx-monitor`, macmini LaunchAgent | SSH-probe every host every **30 min**; can telnet `IW2OHX-4` and re-upload its port config | **unloaded** |
| `fl-sampler.sh`, gw | telnet production every **5 min** | **killed** |

**PC/Flexnet's `3+` interval is only 75-90 min.** A poll every 15 minutes
was landing inside every window we have ever measured. Any previous
stability rate for this link was measured with that in it.

`ping-iw2ohx2.sh` (*/5) is left running — it pings the NAS, not a FlexNet
node.

## Analysis recipe

On `iw2ohx-gw`, against `/tmp/rtr-mon-12/link.pcap0`:

```bash
# every '3+' full-table request -> what we answered -> the next teardown
python3 /tmp/plus.py /tmp/rtr-mon-12/link.pcap0 192.168.1.202 192.168.1.201

# who tore the link down, pinned (NEVER omit --local-ip or --link-only)
cd /home/iw2ohx/xnet_investigation_agent/linbpq-flexnet/tools
python3 axudp_teardown.py --local-ip 192.168.1.202 --peer-ip 192.168.1.201 \
        --link-only /tmp/rtr-mon-12/link.pcap0

# the frames immediately before each teardown
python3 disc_context.py …
```

**Counting rules that have inverted these statistics before:**
- Teardowns arrive in **pairs 60 s apart**; the second is PC/Flexnet's
  fresh-session seed. Count each pair as **one** event.
- A **quiet hour proves nothing** — confirm a `3+` actually arrived.
- PCF's `600` is its session seed, not a verdict on what preceded it.
- The outbound **link-time frame** and the **advertisement-volume spike**
  both correlate strongly with teardowns and are *part of* the `3+`
  answer, so they carry its timestamps. They are artefacts.

**The one thing never yet tested**, and the reason for this run: what
PC/Flexnet does with a **correct but large** answer — 157-171 records at
16 per frame, one frame per 5 s, spread over 40-120 s. Before v2.2.1 that
shape was never emitted, so no earlier capture contains it.
